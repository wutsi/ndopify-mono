# Signed Contract PDF Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Once every party asked to sign has signed a contract, generate, asynchronously, a signed PDF of it (the
original HTML's body + one signature block per signer with a QR code, legal name, signing date/time and signature
hash), store it with the QR code images next to the original HTML, and expose its URL on the contract. Beforehand, salt
each signature's hash so that publishing it can't leak the signer's IP / user agent / e-mail by brute force, and
store the PDF's SHA-256 so that a PDF can later be checked against the one Ndopify generated.

**Architecture:** `ContractService.sign` already publishes `ContractSignedEvent` on the last signature. A new
`@Async @TransactionalEventListener(AFTER_COMMIT)` in `ContractEventListener` calls `SignedContractService.generate`,
which (1) reads the contract and its parties, (2) downloads the original HTML from storage, checks it against
`contentHash`, renders one QR PNG per signer and the PDF, uploads them outside any transaction, then (3) stores the
PDF's URL and SHA-256 under the contract's lock. Rendering is a pure class (`SignedContractRenderer`: Jsoup → XHTML → Flying
Saucer), so it's unit tested without Spring.

**Tech Stack:** Kotlin, Spring Boot, JPA, Flyway, Jsoup (`W3CDom`), Flying Saucer `flying-saucer-pdf` 10.6.0 (OpenPDF),
`qrcode-kotlin-jvm` 4.5.0, Mustache (signature block template), PDFBox (tests only, to read the PDF's text). All
already in `modules/ndopify-server/pom.xml`: **no new dependency**.

**Spec:** The user's request of 2026-10-19 (below, under *Decisions*); no separate spec file.

## Decisions (spec)

- **Trigger:** `ContractSignedEvent` (published by the last required signature). Async, after commit: the signer's
  request never waits for the PDF, and nothing is generated for a rolled-back signature.
- **PDF content:** the `<body>` of the original HTML (its `<head>` is dropped), followed by a *Signatures* section with
  one block per party that **signed** (`signed = true`; the agent of a mandate, `signatureRequired = false`, has no
  block), in the contract parties' order. Each block: QR code, legal name, signing date and time, signature hash.
- **QR code URL:** `{tenant.eSignaturePortalUrl}/verify/{contractId}/{signatureHash}` (trailing `/` of the portal URL
  removed). The verify page itself is **out of scope** (see *Follow-ups*).
- **Dates:** `TenantFormatter(tenant).date(signedAt) + " à " + TenantFormatter(tenant).time(signedAt)`, never a
  hard-coded pattern.
- **Storage:** in the original HTML's directory (the directory of the storage path behind `contentUrl`):
  - `{dir}/signature-{n}.png` per signer, `n` = 1, 2, … in the order of the blocks (never the contract party id: it's
    the secret of the signer's `/sign/{contractPartyId}` link, and these paths are public),
  - `{dir}/{contract.number}.pdf` (readable name for an e-mail attachment).
- **Signature salt:** each signature gets a random salt, `signatureSalt` = 16 bytes from `SecureRandom`, lowercase hex
  (32 chars), generated by `ContractService.sign` and stored in `T_CONTRACT_PARTY.signature_salt CHAR(32)`. It's the
  **first line** of the signature hash's input. Stored only: never in a DTO, never in the PDF, never logged. Why: the
  hash is now public (PDF, QR URL), and its other unknown inputs (IP, user agent, e-mail) are guessable; with 128
  random bits in the input, nobody without the database can test guesses. Existing hashes aren't migrated
  (pre-launch: no deployed data).
- **Contract:** new `signedContentUrl` (nullable) on `ContractEntity`, `Contract` and `ContractSummary`.
- **Signed content hash:** new `signedContentHash` on `ContractEntity` only (`T_CONTRACT.signed_content_hash
  CHAR(64)`): SHA-256 of the exact PDF bytes uploaded (`ContractHasher.contentHash(pdf)`), set with
  `signedContentUrl`, in the same save. Stored only, like `contentHash`: it can't be printed in the PDF (it's the
  hash of the PDF), and exposing it is for the verify page (*Follow-ups*).
- `signatureHash` / `signatureSalt` / `contentHash` / `signedContentHash` **stay out of every DTO**
  (`signatureHash` is printed in the PDF only).
- **Integrity:** if `contentHash` is set and the downloaded bytes don't hash to it, no PDF (logged, `success=false`):
  the signatures were made on other content. A null `contentHash` (content set by the admin endpoint) is accepted.
- **Idempotent:** nothing is generated for a contract that isn't `SIGNED` or already has a `signedContentUrl`.
- **Re-run:** `POST /v1/contracts/{id}/signed-content` (`@OpsEndpoint`, off in prod) runs the same generation
  synchronously, for a failed async run.
- **Fails closed** (logged, no PDF, no exception out of the listener) when: no `contentUrl`, `contentUrl` not from
  the configured storage, no `eSignaturePortalUrl`, content hash mismatch, a signed party without `signatureHash` (or `signatureSalt`).

## Global Constraints

- Follow CLAUDE.md's *Asynchronous e-mails* listener pattern exactly (TenantContext + `DefaultKVLogger`, `finally`
  log + remove), even though this sends no e-mail.
- Tests: `kotlin.test` assertions only; `@MockitoBean`, never `@MockBean`.
- `V4_0__contract.sql` is edited in place (pre-launch, see memory *migrations-editable-pre-launch*).
- Every write of a contract locks it first (`findByIdForUpdate`) — keep it that way.
- No lock and no transaction held during download / render / upload.
- The salt is generated with `java.security.SecureRandom` (one shared instance), never `Random` / `UUID` / the clock.
- French copy in the PDF: section title `Signatures`, labels `Signé par`, `Date et heure`, `Hash de la signature`,
  plus `Scannez le QR code pour vérifier cette signature.` (same wording as the esignature `verify.html` prototype).

## Review Focus

1. **Characters outside WinAnsi** (French `TenantFormatter` output uses U+202F / U+00A0 no-break spaces; names with
   `ŋ`, `ɛ` in Cameroonian names): Flying Saucer's built-in Helvetica drops them. Expect a TTF to be embedded
   (Task 4 test `renders non-latin1 characters`).
2. **MJML output isn't XHTML** (unclosed `<br>`, `<meta>`, MSO conditional comments, `<!--[if mso]>`): Flying Saucer
   needs a well-formed DOM. Expect Jsoup → `W3CDom`, comments and `<script>` removed (Task 4 test `renders the mandate
   contract template`, using the real `search.mjml` output).
3. **The async run fails** (S3 down, render error): the contract stays SIGNED with no PDF, logged with
   `success=false`; the ops endpoint regenerates it (Task 6 test).
4. **Two runs at once** (listener + ops endpoint): the second must not overwrite the first's URL. Expect
   `setSignedContent` under lock to keep an existing URL (Task 5 test `keeps the first signed content`).
5. **Tampered / replaced content** between signature and generation (admin `POST /content` can't happen on a SIGNED
   contract, but a storage file can be overwritten): hash mismatch → no PDF (Task 5 test). Same idea for the salt: two
   signatures with identical inputs (same IP, UA, second) must still get different hashes (Task 1 test `salts differ`).

  ```kotlin
  fun generate(id: String): String? {
      val contract = contractService.findById(id)
      if (contract.status != ContractStatus.SIGNED || contract.signedContentUrl != null) return null

      val tenant = tenantService.findById(TenantContext.get()!!)
      val portalUrl = tenant.eSignaturePortalUrl?.trim()?.removeSuffix("/")?.ifBlank { null }
          ?: return skip(id, "no eSignaturePortalUrl")
      val storage = storageProvider.get()
      val contentPath = contract.contentUrl?.let { url -> storage.pathOf(url) }
          ?: return skip(id, "content not in storage")
      val dir = contentPath.substringBeforeLast('/', "")

      val content = ByteArrayOutputStream().also { out -> storage.get(contentPath, out) }.toByteArray()
      if (contract.contentHash != null && contract.contentHash != ContractHasher.contentHash(content)) {
          return skip(id, "content hash mismatch")
      }

      val signers = contractService.findParties(contract).filter { party -> party.signed }
      if (signers.any { party -> party.signatureHash == null || party.signatureSalt == null }) {
          return skip(id, "signature without hash or salt")

          storage.store(join(dir, "signature-${i + 1}.png"), ByteArrayInputStream(qr), "image/png")

              signatureHash = party.signatureHash!!,
              qrCodePng = qr,
          )

      val pdf = renderer.render(String(content, Charsets.UTF_8), blocks)
      val pdfPath = join(dir, "${contract.number}.pdf")
      storage.store(pdfPath, ByteArrayInputStream(pdf), "application/pdf")

      val url = storage.publicUrl(pdfPath).toString()
      return contractService.setSignedContent(id, url, ContractHasher.contentHash(pdf)).signedContentUrl
  }
  ```

## Risks & assumptions

- **Public PDF URL.** `publicUrl` is used, like the original HTML today: anyone with the URL reads a contract with
  personal data. Same exposure as now, but a PDF is more likely to be forwarded. Consider presigned URLs when e-mailing.
- **The signature hash becomes public** (printed + in the QR URL). Intended (verification); salted (Task 1), so it
  can't be brute-forced back to the IP / user agent / e-mail without the database. Someone with database access still
  can — acceptable, they can read those columns anyway.
- **The PDF isn't tamper-evident by itself**: an edited PDF keeps a valid-looking QR code. `signedContentHash` makes
  the check possible (verify page, follow-up 1) but nothing performs it yet.
- **Head styles dropped** as specified: MJML puts some CSS (`mail.css`, responsive classes) in `<head>`. Most of its
  styling is inline, but check the eyeballed PDF in Task 4; if needed, copy `<head><style>` (not `<link>`, not
  media queries) into the shell — a one-line change.
- **Flying Saucer = CSS 2.1**: no flex/grid. MJML's table layout renders; any future contract template must too.
- `qrcode-kotlin` 4.x API (`QRCode.ofSquares().withSize().build().renderToBytes()`) — confirm against the version in
  the POM when implementing.
